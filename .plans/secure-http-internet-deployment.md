# Secure HTTP for known internet clients — Windows and Linux

> **Status:** Ready for implementation

## Outcome and boundaries

- **Problem and target:** The current HTTP adapter is unauthenticated and intended only for local clients. Enable known native MCP clients to connect through public HTTPS without exposing the backend listener or enabling remote compilation/execution by default.
- **User decisions:** Public HTTPS gateway with bearer tokens initially; documentation-only HTTP by default; compiler/execution tools require explicit opt-in on an isolated host; stdio unchanged; deployment instructions and acceptance on Windows and Linux. Document private VPN/SSH access as the safer alternative. OAuth is deferred.
- **In scope:** Mandatory HTTP authentication, per-client credentials and identity, a process-level tool profile, bounded admission controls, redacted audit events, migration guidance, and one stock Caddy deployment recipe tested on both operating systems.
- **Out of scope:** Native TLS in PureBasic, OAuth/JWT/discovery endpoints, browser clients/CORS, public anonymous tools, uploads/remote filesystem mapping, automatic sandbox provisioning, multi-tenant execution, parallel tool workers, hot credential reload, custom Caddy plugins, changes to stdio protocol/tool schemas, and fixing the existing Windows preload race.
- **Approach:** Extend the existing HTTP adapter, CLI parser, and shared tool registry with narrow mode-aware checks. Keep HTTP/1.1 loopback framing and serialized dispatch. Caddy is an optional deployment component, not a new pbmcp runtime/build dependency. Add tests in the existing HTTP test file; embed the canonical gateway configuration in INSTALL.md instead of creating a deployment framework.
- **Migration:** Intentionally retire unauthenticated HTTP: every `http` invocation requires a credentials file, including local/VPN use. No insecure bypass. Existing local HTTP users must configure a token and, if needed, explicitly enable compiler tools. Stdio/file-test modes retain current behavior.

### Security and public contracts

**Credentials and startup**

- CLI: `pbmcp http [--port N] --auth-file <path> [--allow-compiler-tools]`. Require one nonempty auth-file argument; reject duplicates, missing values, unknown options, and repeated boolean flags with exit 2. Preserve port validation and loopback-only binding. No token values on the command line or in environment variables.
- Credentials file schema: `{"clients":[{"id":"workstation","tokenSha256":"<64 lowercase hexadecimal characters>"}]}`. Permit 1–32 clients; IDs are unique ASCII `[A-Za-z0-9_-]{1,64}`; hashes must be unique. Reject wrong types, missing/unknown fields, invalid hashes, duplicate JSON object members, malformed/unreadable/missing files, and files over 16 KiB. Validate member uniqueness rather than relying on the JSON parser's duplicate-key behavior. Read/validate once before listening; failures never fall back to anonymous access and never echo file contents.
- Each token is a separately generated cryptographically random 32-byte value encoded as 64 lowercase hex characters. Persist SHA-256 of its ASCII token representation, not plaintext. Document Node's built-in crypto generator and hash computation for both OS shells; show the plaintext only at creation and provision it to the client's secret store. Hashes are credential verifiers, not usable bearer tokens.
- Compare a supplied token's digest with fixed-length, full-scan comparisons across every configured client; do not short-circuit by matching prefixes, secret characters or first matching client. Review implementation and generated compiler behavior before describing the comparison as constant-time; timing microbenchmarks alone are not proof. Check PureBasic command documentation before implementation; no new crypto dependency or bespoke cipher.
- Store the verifier file outside source roots and temporary staging; Linux owner-only permissions and Windows protected ACLs. Load it only in HTTP mode. Rotation/revocation is atomic file replacement plus controlled restart; no hot reload or token expiry framework. Deleted clients lose access after restart.

**Authentication and profiles**

- Require exactly one Authorization field on every HTTP request, including initialize, notifications and ping. Scheme is case-insensitive Bearer; credential is case-sensitive fixed-format hex. Missing, wrong or unusable credentials return empty 401 with `WWW-Authenticate: Bearer realm="pbmcp"` and `Cache-Control: no-store`. Duplicate Authorization, comma-joined credentials or ambiguous header syntax return 400. Never accept credentials in queries, cookies, bodies or forwarded identity headers. Keep exact `/mcp` routing; query-bearing paths are rejected and never logged raw.
- Preserve existing structural/framing, Host, Origin and unsupported-method/path checks. Those may return their existing 4xx before authentication; no malformed request may reach dispatch. On an otherwise valid POST, authentication happens at header completion, before waiting for the declared body or parsing JSON. An unauthenticated header-only POST declaring a large body must get 401 promptly. Retain only client identity/index, never bearer text, in connection metadata.
- HTTP default permits exactly pb_docs_search and pb_command. Hide pb_check, pb_run and pb_version from tools/list and reject direct calls to them before entering their handlers, using the existing HTTP 200 MCP `isError` unavailable-tool result. Do not turn disabled-tool errors into transport failures. Unknown tools retain current behavior. Initialization instructions must not recommend unavailable compiler tools.
- `--allow-compiler-tools` permits all five existing tools for every authenticated client of that process, matching current stdio schemas/order. It is not a per-client ACL. Operators needing separate rights use separate instances/hosts and disjoint credentials; do not promise tenant isolation. Stdio/file-test behavior and instructions remain unchanged.
- Both compiler tools are privileged: compilation can read host files and invoke toolchain capabilities; execution can access the service account's files/network. Secrets readable by that account cannot be protected from deliberately malicious code running as that account. Only trusted compiler clients; disposable isolated VM/container, non-admin identity, restricted writable directories and outbound network, no personal/cloud credentials. Token hashes reduce plaintext exposure but do not sandbox the process.

**Admission and audit**

- Preserve 16 accepted backend connections, 16 KiB headers, 1 MiB body, 10-second receive/send bounds, no pipelining/chunked requests and serialized execution. Add a monotonic-time token bucket per configured client: burst 10, refill 1 request/second; consume once at successful header authentication, including notifications/initialize. Exhaustion returns empty 429 with integer Retry-After and Cache-Control: no-store, never executes a tool, and does not consume another client's allowance. Buckets are bounded by the credential list and reset on restart; no IP cache or unbounded request-ID/session registry.
- Unauthorized traffic does not allocate client buckets. Rate-limit repetitive unauthenticated audit events with one aggregate summary per 60 seconds, not sleeps or lockout of valid clients. Existing receive/connection bounds and gateway admission controls bound backend state; these are not volumetric DDoS protection. Recommend an upstream firewall/IP allowlist or edge protection for hostile public environments.
- Emit JSON-line HTTP audit events to stderr with server timestamp, validated client ID (or anonymous), bounded method/tool name, HTTP status, success/tool-error/denied category and elapsed time. One completion event per authenticated message plus sampled rejection summaries. JSON-escape attacker-controlled names and cap them at 80 characters. Never emit Authorization, token/verifier, raw headers/body, source, tool arguments/results, file paths or raw URL/query. No HTTP audit output on stdout and no changes to stdio stderr behavior. Deployments must restrict and rotate captured stderr; do not add an audit database.

**Gateway and deployment**

- Canonical configuration is a marked Caddyfile block in INSTALL.md using environment placeholders for site hostname, backend port and access-log path. Use stock Caddy 2.10+; record the version exercised on each OS. No plugin build or second authentication system: Caddy terminates TLS, pbmcp validates each client's bearer. Preserve Authorization unchanged upstream; never replace all client tokens with a shared backend secret.
- Public side: valid DNS/hostname and public CA certificate, minimum TLS 1.2, HTTPS endpoint only; document certificate issuance/renewal and optional port 80 for ACME/redirect only, never a backend proxy there. Clients start at HTTPS and do not send tokens to HTTP or follow cross-host redirects. Disable public administration/metrics/debug endpoints; keep Caddy admin local or disabled. Only TCP 443 (and optional 80) is opened; use h1/h2, avoiding a needless UDP/HTTP3 firewall dependency.
- Proxy only exact POST `/mcp`; reject other routes/methods and all queries without logging their contents. Preserve Origin so the backend continues rejecting it. Set upstream Host to `127.0.0.1:<backend-port>`; remove Forwarded, X-Forwarded-* and any unused client-identity headers, including automatic Caddy forwarding fields. Upstream HTTP/1.1 with keepalive disabled, no retries, no unbounded buffering. Clients must send known Content-Length; unsupported streaming/chunked input may be rejected rather than weakening backend framing.
- Apply body cap 1048576 bytes, 16 KiB header cap, read-header 10s, read-body 10s, idle 30s; upstream response-header timeout 180s and gateway write timeout 200s so one bounded staged compile/run with compiler retry can complete. Limit concurrently forwarded backend requests to 16 with Caddy's documented overload controls; overload may return 503, never automatic POST retries. Queueing behind serialized tools may still time out: document head-of-line blocking rather than promising 16 parallel jobs or strict wall-clock execution latency.
- Use restricted rolling gateway logs (10 MiB, 5 retained files) without request headers, raw URI/query or response headers; do not enable log_credentials or request-body logging. Backend audit carries client identity; gateway access logs carry network/status information. Auth-file contents are not needed by the Caddy account.
- Linux: dedicated pbmcp user and hardened systemd example, explicit working directory, read-only docs/binaries, writable temp/log paths only, protected auth file, firewall, service restart and log retention. Windows: dedicated non-admin pbmcp account, protected NTFS ACLs, Task Scheduler supervision/restart for the console application, explicit working directory, captured/rotated stderr and firewall. Caddy may use its documented native service mechanism under a restricted separate account; never register pbmcp itself with sc.exe as if it implemented SCM. Keep service snippets in INSTALL.md; do not add a service-management dependency.
- Set PBMCP_PRELOAD=0 in both deployment recipes and deterministic security fixtures because the recorded Windows race is a separate unresolved defect. Native Linux and Windows validation are required; WSL can establish Linux behavior but cannot establish Windows ACL/service behavior.

## Final acceptance

- **Checks:** All T1–T6 tests/builds and operator checks have observable recorded results on Windows and Linux. Credentials fail closed before listen/dispatch; every valid HTTP message authenticates; default docs-only discovery and invocation agree; opt-in remains explicit; stdio stays compatible; admission and retained state are bounded; redacted logs and verified HTTPS preserve the proxy/backend trust boundary.
- **End state:** Known clients can use `https://<hostname>/mcp` with preconfigured bearer headers. The backend remains authenticated IPv4 loopback-only. No public compiler tools by default, no browser/CORS access, no plaintext public MCP endpoint and no automatic tool POST retries. Installation guidance covers migration and both OSes.
- **Deferrals and deployment gates:** OAuth/automatic MCP authorization discovery, untrusted code isolation enforcement, hostile-traffic edge protection and the Windows preload defect remain separate work. Set PBMCP_PRELOAD=0 for this deployment. Real DNS/certificate/firewall/account/supervision checks are release gates, not assumptions.
- **Review limit:** No independent reviewer/delegation tool is available in this session. The author performed the security/complexity checklist and narrowed the design to stock Caddy, existing modules/test files, fixed bounded per-client state and one global HTTP profile. This is a reviewed implementation handoff, not an independent security audit; arrange independent security review before exposing privileged compiler instances.
